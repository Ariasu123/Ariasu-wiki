# vLLM / SGLang 学习路线（个人笔记）

关联阅读：可结合 [Attention 与 GQA](../../llm/01-Architecture-%E6%A8%A1%E5%9E%8B%E6%9E%B6%E6%9E%84/Attention%20%E4%B8%8E%20GQA.md) 理解；推理系统中的 KV Cache 优化依赖注意力结构。


> [!summary]
> 先学 `vLLM`，后学 `SGLang`。
> `Mac` 主要用来建立心智模型和做开发；真实性能实验放到远程 `Linux GPU`。
> 我的目标不该只是“会用”，而应该是“能 benchmark、能 profile、能读代码、能做小改动”。

## 我的判断

- 先学 `vLLM`
  - 更像行业基线
  - 资料和生态更完整
  - 适合先建立标准的 serving 心智模型
- 再学 `SGLang`
  - 不只是 serving engine
  - 还有前端语言 / DSL、结构化生成、prefix reuse 这套思路
  - 更适合在理解基础 serving 后再看
- 如果目标是中国公司的 AI infra
  - 大概率还得继续补 `TensorRT-LLM`、`Triton`、`CUDA/Triton kernel`

一句话：

- `vLLM` = 现代 LLM serving 的标准心智模型
- `SGLang` = 推理引擎 + 可编程前端 + 更复杂缓存 / 调度思路

## Mac 的定位

不要强行追求“全在 Mac 上学完”。

更合理的方式是：

- `Mac` 做学习、开发、代码阅读、toy experiment
- `Linux GPU` 做真实性能测试、profiling、多卡实验

原因：

- `vLLM` 在 macOS Apple Silicon 上只是 experimental
- `vllm-metal` 是 community-maintained，不是最稳妥主线
- `SGLang` 文档主要围绕 NVIDIA GPU
- `Mini-SGLang` 甚至直接是 Linux only

所以 Mac 上的目标不是“跑满”，而是“先把系统理解透”。

## 学这个方向前，先补哪些底子

如果这些不稳，直接上 `vLLM / SGLang` 会很难受：

- Python
- C++（至少能读能改）
- PyTorch 基础
- Transformer 推理流程
- Linux 基础：进程、线程、内存、网络
- Docker
- 基本的 SQL / 缓存 / 消息队列认知

## 我真正要先搞懂的概念

这些比“先装哪个框架”更重要：

- autoregressive decoding
- prefill vs decode
- KV cache
- prefix caching
- continuous batching
- chunked prefill
- quantization
- `TTFT / TPS / latency / P99`

如果这些概念说不清，后面 benchmark 和 profiling 很容易只停留在表面。

## 我的学习路线

### 0. 先补底子（1-2 周）

目标：别让基础知识成为瓶颈。

结果要求：

- 能说清 Transformer 推理主流程
- 能看懂基本 Python / C++ / PyTorch 代码
- 对 Linux / Docker 不陌生

### 1. 先学推理系统，不急着学框架（2 周）

我这阶段应该做的：

- 看 `vLLM` 架构和 V1 blog
- 看 `SGLang` docs 概览
- 看 `Mini-SGLang / nano-vllm`
- 自己写一篇概念笔记
- 最好画一张 request lifecycle 图

这阶段的目标不是跑起来，而是先理解：

- 一个请求怎么进入系统
- prefill / decode 怎么分开
- KV cache 怎么影响吞吐和延迟
- batching / prefix cache 为什么重要

### 2. 在 Mac 上先把 vLLM 跑通（1-2 周）

目标：跑通链路，不追求性能结论。

我要做的：

- build `vLLM CPU` 或尝试 `vllm-metal`
- 启一个 OpenAI-compatible server
- 用 Python client / `curl` 调通
- 观察不同 `max model len / batch / concurrency` 的表现

我要重点掌握：

- 常见 server 参数
- model loading / OOM 问题
- metrics 怎么看

输出物：

- 一个本地可复现 demo
- 一篇简短 benchmark note

### 3. 开始读精简实现（2 周）

阅读顺序：

1. `nano-vllm`
2. `Mini-SGLang`

我读代码时重点不是逐行抠，而是回答：

- 请求怎么排队
- cache 怎么管理
- prefix reuse 为什么能省算力 / 内存
- scheduler 为什么会成为瓶颈
- CPU overhead 为什么会拖垮 GPU 利用率

输出物：

- 一份自己的 code map
- 至少做一个小改动：日志 / 统计 / 简单策略

### 4. 上远程 Linux GPU，先打透 vLLM（2-3 周）

这里才开始接近真正的 infra 训练。

我要做的：

- 跑 `vLLM` 服务
- 跑不同模型、不同并发
- 测 `TTFT / throughput / P99`
- 用 profiler 看热路径
- 学单卡、多卡、`TP / PP`

这一阶段最重要的是：

把“感觉快不快”变成“能解释为什么快 / 慢”。

输出物：

- 一份 benchmark 报告
- 至少拿到一个清晰结论，例如：
  - batch 变化如何影响吞吐
  - 长 prompt 如何影响 `TTFT`
  - prefix cache 命中带来多大收益

### 5. 再学 SGLang（2-3 周）

重点不是只问“它比 `vLLM` 快多少”，而是看它为什么这样设计：

- 为什么要有前端语言 / DSL
- `RadixAttention` 和 prefix reuse 的关系
- 结构化生成、程序式推理场景和普通 serving 有什么不同
- 服务层 / 调度层 / 缓存层和 `vLLM` 的差异

输出物：

- 一份 `vLLM vs SGLang` 对比笔记
- 对比维度至少包括：
  - 易用性
  - 代码可读性
  - 结构化生成
  - serving 特性
  - benchmark 方法

### 6. 长期补底层优化

这部分才是 infra 的真正壁垒：

- CUDA 基础
- Triton
- CUTLASS
- FlashAttention / FlashInfer
- NCCL / 通信
- 多机多卡
- Nsight profiling
- kernel-level bottleneck analysis

这里不需要一口气学满，但至少要逐步把 `CUDA + Triton + profiling` 拉起来。

## 找工作时，什么成果最有用

对招聘方最有说服力的，不是“我学过这些框架”，而是：

- 一个 `vLLM vs SGLang` benchmark repo
- 一份详细 profiling 报告
- 一个真实的小功能 / 小优化 PR
- 一篇系统性技术博客
- 一个把 serving、监控、压测、回归测试串起来的小平台

核心不是“知道”，而是“做过并能解释”。

## 提醒自己不要走偏

- 不要一上来就扎进 kernel 细节
- 不要把“能跑”误认为“理解了系统”
- 不要只盯 benchmark 数字，不看背后的调度 / 缓存 / CPU overhead
- 不要把目标设成“会用 `vLLM` 和 `SGLang`”

更准确的目标应该是：

- 能用它们
- 能 benchmark
- 能 profile
- 能读核心代码
- 能做小改动
- 懂系统和性能分析

## 当前最现实的顺序

1. 先建立 serving 心智模型
2. 用 `vLLM` 建立行业基线认知
3. 用 `SGLang` 扩展到更复杂的 serving 思维
4. 再往 `CUDA / Triton` 深挖
