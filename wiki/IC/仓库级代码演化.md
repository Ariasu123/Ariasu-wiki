
> 概念页：以 HORIZON 论文（arXiv:2606.28279）及其谱系工作（AlphaEvolve、SATLUTION、ABCEvo）为参考整理，面向通用理解。

**仓库级代码演化（repository-scale self-evolution）** 是一种自进化 agent 范式：让 LLM 结合自动评估器，对一个**版本控制下的完整代码仓库**进行持续演化（编辑 → 评估 → 接受/拒绝 → 再编辑），并且**只有通过可执行证据检验的变更才被接受**。它不是修单个函数，而是把整个软件/硬件产物当作可进化的对象。

## 一、核心原则

> 一个候选变更只有通过**可执行正确性检查**并**改善测量到的行为**，才是有用的。

由此推导出的三条工程要求：

1. **可执行评估器**：判断不能靠 LLM 自我感觉，必须有可运行的测试/仿真/证明/评测（evaluator）。
2. **证据门控**：通过评估才 commit，失败必须记录（acceptance predicate 决定接受或拒绝）。
3. **版本控制即基础设施**：git 提供隔离工作区、可回放的历史和附带的评估证据。

这可以看作 [Harness Engineering](../agent-engineering/03-Harness-and-Workflows-%E8%BF%90%E8%A1%8C%E6%A1%86%E6%9E%B6%E4%B8%8E%E5%B7%A5%E4%BD%9C%E6%B5%81/Harness%20Engineering.md) 中"评估与观测/约束校验"层在代码/设计演化场景的极致化：评估器与验收谓词写进环境，而不是写在 prompt 里期待模型自觉。

## 二、演化谱系

| 系统 | 演化对象 | 领域 | 关键点 |
|------|----------|------|--------|
| **AlphaEvolve** | 算法内核（isolated kernels） | 科学/算法发现 | LLM + 自动评估器 + 演化循环发现并改进算法 |
| **SATLUTION** | 完整 C/C++ SAT-solver 仓库 | SAT 求解 | 全仓库规模演化，严格正确性保证 + 分布式运行时反馈，甚至自进化自己的演化规则；最终超过人类设计的 SAT 竞赛冠军 |
| **ABCEvo** | 百万行 ABC 逻辑综合系统 | EDA 软件 | 协调多 LLM agent 在正确性与 QoR 驱动的评估循环下自主重写 EDA 工具 |
| **HORIZON** | RTL 源码、testbench、验证产物 | 硬件设计 | 把同一套"仓库自包含、证据门控"原则用到**设计本身**；详见 [HORIZON RTL 论文精读](HORIZON%20RTL%20%E8%AE%BA%E6%96%87%E7%B2%BE%E8%AF%BB.md) |

前三者演化的是**工程师运行的程序**（solver、synthesis kernel、EDA 工具）；HORIZON 演化的是**工程师设计的产品**（硬件设计）。这种推进让一套协议同时覆盖单任务 RTL 生成、补全和修复——RTL benchmark 问题可以"原样"处理，而不是改写成软件工程的替代问题。

## 三、Git 作为 Agent Substrate

近期趋势是把版本控制本身当作 LLM agent 的脚手架：

- **EvoGit**：用 Git 系统发育图协调一群去中心化 coding agent 的群体演化——无共享内存、无显式消息传递，版本谱系记录完整血统。
- **Git Context Controller**：把 agent 的上下文从瞬态 token 流提升为持久的、版本化的记忆，提供显式 `COMMIT`/`BRANCH`/`MERGE` 操作，服务长程软件任务。
- **HORIZON**：把一次硬件设计问题托管为自包含、验证门控的仓库，**历史即可回放的经历 trace**。

三者不约而同表明：git 的分支、血统、检查点语义天然适合组织 agentic 探索——**仓库原生 agent 正在成为范式，而非单一领域的技巧**。这也与 [Loop Engineering](../agent-engineering/03-Harness-and-Workflows-%E8%BF%90%E8%A1%8C%E6%A1%86%E6%9E%B6%E4%B8%8E%E5%B7%A5%E4%BD%9C%E6%B5%81/Loop%20Engineering.md) 的"把记忆放在磁盘上而不是上下文里"原则完全一致。

## 四、关键设计维度

- **接受谓词（acceptance predicate）**：决定 commit 还是 reject，是整个范式正确性的锚点。HORIZON 中它是 benchmark 的 pass 条件，因此会出现"通过即停"（覆盖率作为观察信号而非目标）。
- **反馈接口**：agent 能看到多细的评估信号？信号太丰富可能诱发 over-solving/reward hacking（针对可见测试定制产物）；信号太稀疏又让修复无从下手。SWE-bench 用推理期隐藏测试来分离诊断反馈与最终评分。
- **反馈延迟**：评估器越快，迭代修复越可行；真实场景（综合、布局布线、signoff）评估以小时/天计，改变整个系统设计。
- **经验缓冲**：仓库历史同时是正负样本库——成功的修复策略与失败的编辑路径都被记录，供未来迭代或离线 agent-RL 复用。
