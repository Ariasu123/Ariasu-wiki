
## 一、总览

关联阅读：可结合 [Claude Code 代码检索](../02-Coding-Agents-%E7%BC%96%E7%A8%8B%E6%99%BA%E8%83%BD%E4%BD%93/Claude-Code-Internals-%E6%BA%90%E7%A0%81%E5%8E%9F%E7%90%86/%E4%BB%A3%E7%A0%81%E6%A3%80%E7%B4%A2%E6%80%BB%E7%BB%93.md) 理解；通用 RAG 原理可用于分析代码仓库检索。


RAG 的核心是 Retrieval-Augmented Generation，也就是“检索增强生成”。它不是让模型把所有知识都记进参数里，而是在生成答案前先从外部知识库检索相关内容，再把检索结果作为上下文交给大模型回答。

可以用一句话概括：

> RAG = 外部知识库检索 + 上下文注入 + LLM 基于资料生成。

完整 RAG 系统一般分为两个阶段：

| 阶段 | 核心流程 | 说明 |
| --- | --- | --- |
| 离线建库 | 文档加载 -> 文档切分 -> Embedding -> 向量入库 | 把原始知识加工成可检索的索引 |
| 在线问答 | Query 处理 -> 检索召回 -> Rerank -> Prompt 拼装 -> LLM 生成 | 用户提问时实时检索并生成答案 |

## 1. 什么是 RAG？完整 RAG 系统的工作流程是什么？

### 核心回答

RAG 全称是 Retrieval-Augmented Generation，中文是检索增强生成。它解决的是 LLM 知识冻结、无法覆盖私有数据和最新信息的问题。做法是在生成答案之前，先从外部知识库检索相关内容，再把检索结果和用户问题一起交给 LLM，让模型基于这些上下文回答。
### 细节

RAG 的完整流程分为**离线和在线**两个阶段。

离线阶段负责建库：

- 文档加载：读取 PDF、网页、Markdown、数据库等原始数据。
- 文档切割：把长文档切成 chunk，避免整篇文档太长、语义过散。
- 向量化：用 Embedding 模型把每个 chunk 转成向量。
- **入库：把向量、原文和 metadata 一起写入向量数据库。

在线阶段负责问答：

- Query 处理：对用户问题做改写、扩展或 HyDE。
- 向量检索：把 Query 转成向量，到向量库召回相关 chunk。
- Rerank：对粗排结果重新排序，筛掉噪音。
- Prompt 拼装：把问题和参考资料组合成提示词。
- LLM 生成：模型基于资料回答，并**可附上来源。

RAG 的核心价值是**知识可热更新、答案可溯源，不需要频繁重新训练模型**。
### 面试提醒

不要只说“RAG = 检索 + 生成”。要说清楚它解决什么问题、为什么不直接微调、离线和在线流程分别做什么。

## 2. 大模型的 RAG 主要用来解决什么问题？

### 核心回答

RAG 主要解决三个问题：**知识时效性、私有知识覆盖、幻觉**。三者的根源都是模型知识被固化在参数里，训练完成后无法实时更新，也无法天然知道企业内部或垂直领域数据。
### 细节

- 知识时效性：LLM 的训练数据有截止日期，训练后发生的新事件它不知道。
- 私有知识缺失：企业内部文档、项目资料、产品手册通常没有进入训练集。
- 幻觉：当模型没有可靠知识依据时，容易编造看似合理但实际错误的答案。
### 面试提醒

幻觉不是 RAG 唯一解决的问题，它更像**知识缺失的副产品**。面试时要强调 RAG 解决的是“知识如何进入模型推理过程”的根因。

## 3. RAG 和微调各自解决什么问题？优劣势是什么？

### 核心回答

RAG 和微调不是互相替代关系。微调是改模型参数，适合改变模型行为、风格和专业能力；RAG 不改模型参数，而是在推理时检索外部知识，**适合知识频繁更新、需要溯源的问答场景**。
### 细节

| 维度 | RAG | 微调 |
| --- | --- | --- |
| 本质 | 推理时注入外部知识 | 训练时更新模型参数 |
| 适合 | 知识库问答、企业文档、最新信息 | 输出风格、格式约束、专业任务能力 |
| 更新成本 | 低，更新知识库即可 | 高，需要重新训练或继续训练 |
| 可溯源性 | 强，可返回引用来源 | 弱，知识在参数里不可直接追踪 |
| 主要风险 | 检索质量决定上限 | 成本高，更新慢，可能遗忘原能力 |

常见组合是：微调解决“怎么说”，RAG 解决“说什么”。例如**先微调模型适应行业表达，再用 RAG 注入最新业务知识**。
### 面试提醒

不要把 RAG 和微调说成二选一。正确答案是按场景选型，并说明两者可以组合。

## 4. RAG 中的文档怎么存？Chunking 策略是什么？

### 核心回答

先切成 chunk。每个 chunk 会向量化后作为一条记录存储，记录通常包含**向量、原始文本和 metadata。向量用于检索，原文用于让 LLM 阅读，metadata 用于过滤和溯源。**
切割粒度没有固定答案，通常 500 到 1000 个 token 是一个合理的起点，但更重要的是根据文档类型来选策略。**普通文本用固定大小加重叠，有标题结构的文档按语义边界切，代码按函数切，如果既要检索精度又要上下文完整的话，我会用父子切割，也就是小块检索、大块返回。**
### 常见 Chunking 策略

- 固定大小切割：按 token 或字符数切，简单稳定。
- 重叠切割：相邻 chunk 保留 overlap，减少语义断裂。
- 按语义边界切割：按标题、段落、句子等自然结构切。
	**实际操作时，常见的做法是维护一个分隔符优先级列表，先尝试按段落切，切出来太大再按句子切，还是太大再按标点切，以此类推，直到满足 chunk_size 限制。

- **代码切割**：按函数、类、模块边界切。
- **表格切割**：要整块保留，转成 Markdown 格式存储，不能按行截断。表格的每一行都依赖表头才有意义
- **父子切割**：小 chunk 用于精准检索，大 chunk 用于返回上下文，**存储存两份
	- 存储量更大，因为要存父 chunk 和子 chunk。
	- 通过 parent_id 关联
![](../_assets/RAG-%E6%A3%80%E7%B4%A2%E5%A2%9E%E5%BC%BA%E7%94%9F%E6%88%90/Pasted%20image%2020260610151630.png)
### 面试提醒

回答 Chunking 时要同时讲“为什么不能整篇存”“怎么切”“粒度怎么选”。高质量场景可以主动提父子切割。

## 5. 怎么规避语义被切割掉的问题？

### 核心回答

规避语义截断可以从**两个方向入手**：切的时候尽量不破坏语义，切完之后在检索时把上下文补回来。常见方案包括重叠切割、语义边界切割、句子窗口检索、父子切割和 Contextual Retrieval。

### 细节

切的时候避免截断：

- 重叠切割：相邻 chunk 共享一部分内容。
- 语义边界切割：按句子、段落、标题等自然边界切。
- 命题化切割：把复杂段落拆成更独立的事实命题。

检索时补上下文：

- 句子窗口检索：命中某个句子后，把前后几句一起返回。
- 父子切割：小块负责召回，大块负责提供完整上下文。
- Contextual Retrieval：在 embedding 前，让大模型为每个 chunk 生成背景说明，再把背景和 chunk 一起向量化。**通常需要配合 Prompt Caching 控制费用**

### 面试提醒

不要只回答“加 overlap”。更完整的回答是：

语义截断的本质是 chunk 脱离上下文后语义变弱，导致检索召回不到。解决方案分两类：  
**一类是在切的时候避免截断**，比如重叠切割、语义边界切割；  
另一类是在**切完后补上下文**，比如句子窗口检索、父子切割、命题化切割和 Contextual Retrieval。  
实际工程里通常组合使用：**overlap 兜底，语义边界切割保证基础质量，高质量场景再加父子切割或 Contextual Retrieval。**

## 6. RAG 中 Embedding 是什么？如何选择和评估 Embedding 模型？

### 核心回答

Embedding 是把文本转成向量的过程。关键点是**语义相近的文本，向量的余弦相似度高**。RAG 的语义检索就是基于这个特性实现的。

### 细节

选择 Embedding 模型时主要看：

- **语言能力**：中文场景优先看 BGE、Qwen Embedding 等中文效果好的模型。
- **向量维度：维度高通常表达能力更强，但存储和检索成本也更高。
- **最大输入长度：决定单个 chunk 能处理多长。
- 部署方式：云 API 简单，本地部署更适合数据合规场景。
- 业务评测表现：不要只看通用榜单，要在自己的数据集上评估。

 **常见 Embedding 模型**
    
    - **OpenAI text-embedding 系列**：调用方便，英文效果好，但有费用和数据出境问题。
    - **BGE 系列**：中文场景常用，可本地部署。
    - **bge-m3**：适合中英混合、多语言、多模式检索。
    - **Qwen3-Embedding**：中文效果强，适合新项目重点评估。
    - **Voyage、Cohere、Gemini Embedding**：英文或长上下文场景可关注。

**常用评估指标**：

- Hit@K：正确文档是否出现在前 K 个召回结果中。
- MRR：正确结果排得越靠前，分数越高。
- 业务数据集评测：最能反映真实效果。

### 面试提醒

**Embedding 是把文本转成语义向量，让语义相近的内容在向量空间里距离更近。RAG 用它来做语义检索。选模型时不能只看 MTEB 排行榜，要结合语言场景、数据合规、向量维度、输入长度和业务数据上的 Hit@K 评测结果来决定。**

## 7. Embedding 有哪些算法？

### 核心回答

Embedding 算法大致经历了三代：**静态词向量、上下文相关向量、句子级对比学习**Embedding。RAG 场景常用的是第三代，因为它能提前把文档向量算好，查询时只需要算一次 Query 向量。
### 细节

| 代际 | 代表算法 | 特点 | 局限 |
| --- | --- | --- | --- |
| 静态词向量 | Word2Vec、GloVe | 每个词一个固定向量 | 处理不了多义词 |
| 上下文向量 | BERT | 同一个词在不同上下文有不同表示 | 句子相似度检索成本高 |
| 句子级 Embedding | SBERT、SimCSE、BGE | 独立编码句子或段落，适合向量库检索 | 需要针对检索任务评测 |

RAG 常用 **bi-encoder**架构：文档和 Query 分别编码成向量，然后用余弦相似度或内积做检索。

### 面试提醒

要讲出演进逻辑：Word2Vec 解决词向量，BERT 解决上下文语义，SBERT/BGE 解决大规模相似度检索效率问题。

## 8. 什么是向量数据库？如何选型？

### 核心回答

**向量数据库是专门用于存储和检索高维向量的数据库，核心能力是 ANN，也就是近似最近邻搜索**，普通关系型数据库的 B-tree 索引不适合高维向量相似度检索，因此需要专门的向量数据库。
### 细节

常见选型：

- **Chroma**：适合本地开发和快速 Demo，零配置上手快。
- **Qdrant**：适合中小规模生产环境，API 简洁，性能稳定。
- **Milvus**：适合大规模和分布式场景。
- Pinecone：云托管方案，省运维。
- pgvector：已有 PostgreSQL 时可以直接扩展，减少组件复杂度。

选型维度：

- **数据规模**：几万、百万、千万甚至亿级。
- **部署方式**：本地、私有化、云托管。
- 混合检索：是否需要向量 + 标量过滤 + 关键词混合。
- **运维能力**：团队是否能维护分布式向量库。

常见索引算法：

- **HNSW**：查询时从高层粗略定位、再到底层精细搜索，优点是召回率高、查询速度快，但内存占用较大。
- **IVF**：先把向量划分到多个簇里，查询时只搜索最相关的几个簇，优点是适合大规模数据、内存更省，但召回率依赖聚类质量和搜索簇数量
### 面试提醒

不要把向量数据库理解成“普通数据库加一个向量字段”。核心是 ANN 检索能力。选型要结合规模、部署、混合检索和运维成本。

## 9. 向量数据库生产实践：数据量级、性能和瓶颈

### 核心回答

生产环境中要回答清楚使用的向量数据库、数据量级、向量维度、索引类型、查询延迟和遇到的瓶颈。例如百万级向量可以使用 Milvus 或 Qdrant，HNSW 索引下单次查询延迟通常可以做到几十毫秒级。
### 细节

常见性能指标：

- 数据量：例如 100 万到 150 万条向量。
- 向量维度：例如 768、1024、1536 维。
- 索引类型：HNSW、IVF、PQ 等。
- 延迟：P50、P95、P99，而不是只说“很快”。
- 并发：QPS 和稳定性。

常见瓶颈：

- 内存压力：高维向量存储成本大，可用 SQ8、PQ 等量化降低内存。
- 批量写入抖动：大量写入和后台 segment 合并可能影响查询延迟。
- 索引构建耗时：大规模数据重新建索引成本高。
- 过滤条件慢：向量检索叠加 metadata 过滤时要关注索引支持。

### 面试提醒

回答生产实践时要给具体数字，例如数据量、维度、P50/P99 延迟和 QPS。再讲一个真实瓶颈和解决方案，会比泛泛说“用过 Milvus”可信得多。

## 10. 使用 RAG 给大模型一个输入，系统工作流程是什么？

### 核心回答

RAG 在线流程不是直接把用户问题丢给大模型，而是先经过“检索 -> 整理 -> 生成”的流水线：Query 预处理、Query Embedding、向量检索和多路召回、Rerank、**Prompt 拼装、LLM 生成与溯源。
### 细节

在线流程：

- **Query 预处理**：改写、扩展、HyDE（让 LLM 先「假设」一个可能的答案，用这个假设答案的向量去检索）、多角度表达。
- Query Embedding：必须使用和建库时一致的 Embedding 模型。
- 粗召回：向量检索、BM25、多路召回（**RRF合并**）。
- Rerank 精排：用 **Cross-Encoder 等模型重新判断 Query 和候选 chunk 的相关性。
- Prompt 拼装：把资料、问题、回答约束放入 prompt。
- LLM 生成：基于资料回答，最好**附带引用来源。

**Prompt 中常见约束：
- 只能根据给定资料回答。
- 资料不足时说不知道。
- 引用资料来源编号。
### 面试提醒

不要只说“检索 + 生成”。在线流程至少要讲出 Query 处理、召回、Rerank、Prompt 拼接和溯源。

## 11. 向量检索和关键词检索有什么区别？

### 核心回答

关键词检索**依赖词频和精确匹配**，典型算法是 BM25；对**精确词汇命中率极高**，**遇到同义词就束手无策**
向量检索依赖语义空间距离，能找表达不同但含义相近的内容，**语义理解能力强**，**对精确词汇不敏感**
### 细节

| 维度 | 关键词检索 | 向量检索 |
| --- | --- | --- |
| 原理 | 词频、倒排索引、BM25 | Embedding 向量相似度 |
| 擅长 | 专有名词、型号、数字、精确词 | 同义表达、语义相关、模糊问题 |
| 不擅长 | 同义词、改写表达 | 精确匹配、短词、代号 |
| 常见问题 | 用户换种说法就召不回 | 产品型号、编号可能漏召回 |

混合检索做法是**两路并行召回**，再用 RRF 等算法融合排序，最后送入 Rerank。
**BM25：**  
BM25是一种关键词检索算法，在TF-IDF（词频-稀缺性）基础上增加了**词频饱和**和文档长度归一化
**RRF**:
RRF 用排名的倒数来打分，排名越靠前倒数越大，最终按总分降序排列
### 面试提醒

不要说“向量检索一定比关键词检索好”。正确答案是两者互补：向量管语义，BM25 管精确词。

## 12. 如何润色用户 Query？Query Rewrite 的目的是什么？
### 核心回答

Query Rewrite 的目的是**弥合用户提问和知识库文档表述之间的语义鸿沟**。用户问题往往口语化、模糊、有缩写，而文档是正式、结构化、领域化表达，直接检索可能召不回正确内容。

### 细节

常见方法：

- **直接改写**：把口语化问题改成更清晰、正式、完整的问题。
- **Query** 扩展：补充相关关键词、同义词和领域术语。
- **HyDE**：先让 LLM 生成一个假设答案，再用假设答案向量去检索。
- **Step**-**back** **Prompting**：把具体问题抽象成更上层的问题，检索背景知识。
- **多 Query 改写**：生成多个不同角度的问题并行检索。

不同方法解决的问题不同：

- 表达模糊：直接改写。
- 文体差异：HyDE。
- 问题过窄：Step-back。
- 召回角度单一：多 Query 扩展。

### 面试提醒

Query Rewrite 不是简单“润色文字”，而是提升检索召回率。回答时要说出不同改写方法分别解决什么问题。

## 13. 什么是多路召回？具体怎么做？

### 核心回答

多路召回是同时使用多种检索方式获取候选内容，然后融合排序。它的核心出发点是任何单一路径都有盲区，向量检索擅长语义，BM25 擅长精确词，多 Query 扩展能覆盖不同表达方式。

### 细节

常见多路组合：

- 向量检索：召回语义相近内容。
- BM25：召回精确关键词、型号、编号。
- 多 Query 检索：同一问题改写成多个版本分别检索。
- **metadata 过滤：按文档类型、时间、权限、业务线过滤。**

结果融合：

- **去重：同一 chunk 或同一文档重复命中要合并。
- RRF：按排名而不是原始分数融合多路结果。
- Rerank：融合后的候选再做精排，选出最终上下文。

### 面试提醒

调大 top-K 或换 Embedding 模型不一定能解决精确词漏召回。多路召回的本质是用不同检索方式互补盲区。

## 14. RAG 检索优化策略有哪些？
### 核心回答

RAG 检索优化可以分为四层：索引层、查询层、召回层、重排序层。索引层决定知识怎么存，查询层决定问题怎么转换，召回层决定从哪些路径找，重排序层决定最终哪些内容进入 prompt。
### 细节

四层优化框架：

| **层级**   | 解决问题       | 常见方法                                        |
| -------- | ---------- | ------------------------------------------- |
| **索引层**  | 知识怎么存chunk | Chunking、父子切割、metadata、Contextual Retrieval |
| **查询层**  | 问题怎么转query | Query Rewrite、HyDE、Step-back、多 Query        |
| **召回层**  | 从哪些路径找     | 向量检索、BM25、多路召回、过滤召回                         |
| **重排序层** | 谁最相关       | Cross-Encoder Rerank、规则过滤、阈值门控              |

典型生产组合：

- Parent-Child 索引提升上下文完整性。
- 向量 + BM25 多路召回提升覆盖率。
- Rerank 提升最终进入 prompt 的准确性。
- 检索质量门控避免低质量上下文导致幻觉。

### 面试提醒

不要只罗列“换模型、调 top-K”。要从四层框架说清每层解决什么问题，以及它们如何配合。

## 15. 了解哪些更复杂的 RAG 范式？

### 核心回答

RAG 从 Naive RAG 演进到 Advanced RAG 和 Modular RAG。更高级的范式包括 Self-RAG、CRAG、GraphRAG 和 Agentic RAG，它们分别解决是否需要检索、检索质量差怎么办、跨文档全局理解、多轮动态检索等问题。

### 细节

| 范式           | 核心思想                             | 解决的问题       |
| ------------ | -------------------------------- | ----------- |
| Naive RAG    | 基础检索 + 生成                        | 最简单的外部知识注入  |
| Advanced RAG | 检索前后做优化(Query 改写、Rerank、混合检索)    | 改善召回和生成质量   |
| Modular RAG  | 各环节模块化组合                         | **支持灵活编排**  |
| Self-RAG     | **LLM 自己判断是否检索、检索是否有用**          | **避免无意义检索** |
| CRAG         | **检索质量差时自动纠错或降级走网络搜索**           | **检索失败兜底**  |
| GraphRAG     | 用知识图谱和社区摘要增强全局理解                 | 跨文档关联和全局问题  |
| Agentic RAG  | 把 RAG 做成 Agent 循环，LLM决定是否检索，检索几次 | 复杂问题多轮检索和推理 |
GraphRAG 的做法分两步：

1. **预处理阶段**
    - 用 LLM 从文档中抽取实体和关系。
    - 构建知识图谱。
    - 用社区发现算法，比如 Leiden，把关系紧密的实体聚成一个个社区。
    - 再让 LLM 为每个社区生成摘要，形成从细粒度到粗粒度的层次化摘要。
2. **查询阶段**
    - 如果是**局部问题**，比如“某公司 CEO 是谁”，可以直接做实体查找和关系遍历。
    - 如果是全局问题，比如“这批文档主要讲了什么”，就让 LLM 读取多个**社区摘要**，再用 Map-Reduce 的方式汇总答案。

### 面试提醒

不要只背名字。要说明每种范式解决了朴素 RAG 的哪个痛点、核心机制是什么、适合什么场景。

## 16. 什么场景下用图数据库增强向量检索？

### 核心回答

当业务问题涉及**多个实体之间的关联推理**时，可以考虑用图数据库增强向量检索。向量检索擅长找和问题相似的文本，但不擅长沿着实体关系做多跳推理。

### 细节

适合图数据库的场景：

- 企业关系分析：公司、股东、投资方、关联企业。
- 医疗知识图谱：疾病、症状、药物、禁忌关系。
- 代码依赖分析：模块、函数、调用链、依赖关系。
- 供应链溯源：供应商、物料、批次、风险传导。

组合方式：

- 向量检索先定位相关实体或文档。
- 图数据库沿关系边做多跳遍历。
- **合并图谱结果和文本 chunk**。
- 交给 LLM 生成答案。

### 面试提醒

判断标准很简单：如果答案藏在多个实体的关系链里，向量检索通常不够；如果只是查某段描述性内容，向量检索就够了。

## 17. 如何规避 RAG 系统中大模型的幻觉？

### 核心回答

RAG 幻觉主要来自**两类**问题：**检索没有召回相关内容**，模型只能凭自身知识编；检索到了内容，但模型没有严格遵循资料，**生成层额外发挥**。规避幻觉要同时从检索层和生成层控制。
### 细节

常见策略：

- **Prompt 强约束：要求模型只基于资料回答，资料没有就说不知道。
- 检索质量门控：**Rerank 分数低于阈值时拒答或提示资料不足。
- 生成后引用核查：再**调用一次LLL,做审查**，关键结论必须能在 chunk 中找到依据。
- **结构化输出溯源：每条结论附来源编号。

低成本高收益组合：

- Prompt 强约束。
- 检索质量门控。
- 引用来源展示。
### 面试提醒

“检索做好了就不会幻觉”是不对的。RAG 幻觉既可能来自检索失败，也可能来自生成时超出资料。核心原则是：治幻觉，先治检索，再控生成。

## 18. 怎么量化 RAG 效果？

## 19. RAG 知识库如何动态和持续更新？

### 核心回答

知识库更新的核心是文档变了，对应 chunk 和向量也要跟着变，而且要**增量处理**，不能每次全量重建。常见方案是用**内容 hash 检测变化**，文档更新后先删除该文档的旧 chunk，再重新切割入库。
### 细节

常见流程：

- 给每个文档计算内容 hash（比如 MD5 或 SHA256）。
- 通过定时轮询、Webhook 或 Kafka 感知变更。
- 新增文档：切割、向量化、入库。
- 修改文档：删除旧文档对应的所有 chunk，再重新切割入库。
- 删除文档：根据 document_id 删除对应 chunk 和向量。

**全量重建什么时候用**  
    全量重建逻辑简单，但成本高、耗时长，不适合日常更新。  
    适用场景主要有两个：
    
    - 知识库很小，重建成本低；
    - 发生重大架构变化，比如换 Embedding 模型、改 Chunking 策略，新旧向量不兼容。

生产建议：
- 工程上还可以先用“最后修改时间”粗筛，只对**时间戳变化的文档计算 hash，降低成本
- 低频更新：定时轮询 + hash 检测。
- 高频更新：事件驱动 + 消息队列kafka。
- 必须**维护 document_id 与 chunk_id 的关联**，便于删除和重建。
### 面试提醒

知识库更新的关键词是“增量、hash、先删后增、事件驱动”。不要说每次全量重建，也不要轻易说只改某一个 chunk。

## 20. RAG 实际落地中最难的地方是什么？

### 核心回答

RAG 最难的不是跑 Demo，而是把系统调好。真正困难通常集中在三块：**文档预处理、检索质量调优、效果评估**。
### 细节

文档预处理难：

- PDF、表格、图片、扫描件、复杂排版容易解析失败。
- **表格和代码类**文档需要特殊解析策略。
#### 做法：
1. **复杂文档要用专门解析工具**  
    比如 PDF 表格可以用 pdfplumber，不同格式文档可以用 unstructured 做专项解析。
2. **高价值复杂文档可以用多模态模型**      
3. **不同文档格式都有坑**
    - 扫描版文档：需要 OCR。
    - 图片密集文档：关键信息可能藏在图片里。
    - 代码文档：切割不当会破坏逻辑完整性。
    - PDF 表格：普通文本解析容易乱序或丢结构。

unstructured 更适合做 RAG 文档入库前的通用解析。它会把 PDF、Word、PPT、HTML、图片等文档切分成 Title、NarrativeText、ListItem、Table 等**结构化元素**，这样后续可以根据元素类型做 chunking、metadata 标注、表格转 Markdown 或 HTML，再写入向量库和图谱数据库。

文档上传
  ↓
判断文件类型
  ↓
普通 PDF 文本：pypdf / pdfplumber
  ↓
复杂表格 PDF：pdfplumber
  ↓
复杂版面 / 多格式文档：unstructured
  ↓
扫描件 / 图片：OCR + 视觉模型
  ↓
统一转成 DocumentChunk
  ↓
写入 ChromaDB / Neo4j
