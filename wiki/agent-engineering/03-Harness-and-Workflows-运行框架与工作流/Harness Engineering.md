## Harness Engineering 总结

关联阅读：可结合 [Agent 核心问题](../01-Foundations-%E5%9F%BA%E7%A1%80%E6%A6%82%E5%BF%B5/Agent_16.md) 理解；Harness Engineering 面向的是 Agent 系统的可靠交付。


Harness Engineering 是围绕大模型搭建一套可靠运行环境，让 Agent 在长链路任务中能够稳定执行、及时纠偏、失败恢复。

核心思想是：

> Agent 每犯一次错误，就把解决方法固化到环境中，避免以后重复犯错。

可以概括为：

```
Agent = Model + Harness
```

Harness 主要包含六部分：

1. **信息管理**：只向模型提供当前任务真正需要的信息，避免信息过载。
2. **工具系统**：限制工具数量，明确调用条件，过滤工具返回结果。
3. **任务编排**：管理任务步骤、依赖关系、执行进度和停止条件。
4. **记忆与状态**：把任务进度、用户偏好等保存到文件或数据库，支持跨轮恢复。
5. **评估与观测**：通过 Eval 测试集、日志和 Trace 判断 Agent 是否真的完成任务。
6. **约束与恢复**：设置权限、预算、最大步数、输出校验、失败重试和人工接管。

核心工程原则：

- **状态外化**：把进度写入文件，必要时重置上下文后继续。
- **生产验收分离**：不要让同一个 Agent 既执行又给自己打分。
- **优先改环境**：Agent 失败时，补工具、测试、反馈和约束，而不是只要求模型更认真。
- **规则按需加载**：规则文件保持精简，详细内容拆分到独立文档。
- **持续偿还技术债**：把代码原则固化，让后台 Agent 定期扫描并修复。
- **优先成熟技术**：稳定、文档丰富的技术栈通常更容易被 Agent 正确使用。

一句话总结：

**模型决定 Agent 能做什么，Harness 决定它能否稳定、可控、可恢复地把事情做完。**

## Harness 的六层结构

### 1. 上下文精细化管理

解决的问题是：

> 模型这一轮应该看到什么？

核心做法：

- 明确角色、目标和成功标准；
- 只加载当前任务需要的信息；
- 使用即时检索，避免一次性塞入全部资料；
- 分离固定规则、动态证据和中间结论；
- 防止无关信息造成上下文腐化。

这一层管理的是“空间”，也就是当前这次模型调用的上下文如何组织。

### 2. 工具系统的可控调用

解决的问题是：

> 模型应该使用什么工具，以及如何安全使用？

核心做法：

- 只提供完成任务真正需要的工具；
- 明确每个工具的触发条件；
- 避免工具数量过多导致模型选错；
- 对工具返回结果先过滤、提炼，再放入上下文；
- 对高风险工具增加权限、白名单和人工确认。

工具不是越多越好，工具少而清晰通常更稳定。

### 3. 任务执行的全局编排

解决的问题是：

> Agent 当前在哪一步，下一步应该做什么？

常见编排模式：

- ReAct：思考、行动、观察、继续思考；
- Plan-and-Execute：先生成全局计划，再逐步执行；
- Reflexion：失败后反思并调整；
- Tree of Thoughts：并行探索多个方案后选优。

编排层需要提供：

- 明确的任务阶段；
- 子任务依赖关系；
- 当前进度；
- 最大执行步数；
- 完成和停止条件。

它的作用是给 Agent 铺设轨道，避免每一步都会做，但整体任务跑偏。

### 4. 记忆与状态的分层管理

解决的问题是：

> 模型跨轮、跨会话应该记住什么？

状态应该外化，而不是全部依赖上下文窗口。

常见分层：

|状态类型|生命周期|示例|
|---|---|---|
|会话中间结果|当前轮次|临时推理、候选方案|
|任务状态|当前任务|已完成步骤、待办事项、进度|
|长期记忆|跨任务|用户偏好、项目规则、历史经验|

长期任务可以把进度写入文件、数据库或 Git。新一轮使用干净上下文，通过读取状态文件恢复任务。

核心原则是：

> 状态沉到外部存储中，上下文窗口可以随时重置。

### 5. 独立评估与可观测体系

解决的问题是：

> Agent 做得好不好，有没有客观尺子？

主要包括两部分：

**Eval 测试集**

- 收集典型真实任务；
- 标注正确答案或通过标准；
- 每次修改 Prompt、规则、工具或流程后重新运行；
- 对比成功率，防止改进一个问题却引入回归。

**Trace、日志和指标**

需要记录：

- 每一步的决策；
- 工具调用及返回结果；
- token 消耗；
- 执行时间；
- 失败位置；
- 重试次数。

可观测性让调试从“猜哪里错了”变成“直接查看执行轨迹”。

如果需要把这些要求落实为统一平台，可以使用 [Langfuse](Langfuse.md) 组织嵌套 Trace、成本与延迟指标、质量 Score 和数据集实验。

### 6. 约束校验与失败恢复

解决的问题是：

> Agent 出错后能否及时停止并恢复？

这一层包括三部分：

**约束**

- 最大执行步数；
- token 和费用预算；
- 工具权限；
- 可操作资源范围；
- 禁止执行的危险动作。

重要约束最好硬编码，不要只写在 Prompt 里期待模型自觉遵守。

**校验**

- 输出格式校验；
- 类型和参数检查；
- 单元测试；
- linter；
- 白名单校验；
- 真实环境验收。

**恢复**

- API 限流后退避重试；
- 工具失败后换备用路径；
- 发送失败后写入本地队列；
- token 即将耗尽时保存进度；
- 达到最大重试次数后停止或转人工。

[AgentScope 2.0](../04-References-%E9%A1%B9%E7%9B%AE%E5%8F%82%E8%80%83/AgentScope.md) 将上下文压缩、Toolkit、Permission、显式 State、Middleware、Workspace 和 Agent Service 组合成可复用 Harness；质量评测与发布门禁则仍需项目或外部平台补齐。

## 如何逐步建设 Harness

六层不需要一次全部搭完。可以从 Agent 的实际错误反推改进位置：

这种从实际失效事实、交付目标和硬约束反推工程层次的过程，也是 第一性原则 在 Agent 工程中的应用：先识别问题的基本要素，再选择框架与组件。

|Agent 的问题|应改进的 Harness 层|
|---|---|
|经常漏掉信息|上下文管理|
|总是选错工具|工具系统|
|执行顺序混乱|任务编排|
|跨轮忘记进度|记忆与状态|
|无法判断效果|评估与观测|
|失败后直接崩溃|约束与恢复|
