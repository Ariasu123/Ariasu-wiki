
文章核心讨论：**为什么 Claude Code 使用 `Grep + Glob + Read`，而不是给代码库建立 RAG 向量索引？**
### 一、RAG 在代码场景的问题

关联阅读：可结合 [Claude Code 架构](Claude%20Code%E6%9E%B6%E6%9E%84%E8%AE%BE%E8%AE%A1.md) 理解；架构设计给出检索工具在执行链中的位置。


1. **切片破坏代码结构**  
    函数、类和调用关系可能被拆开，导致上下文不完整。
2. **不擅长精确匹配**  
    向量检索寻找“语义相似”，但代码经常需要准确找到 `getUserById` 这样的符号。
3. **索引容易过期**  
    代码持续变化，需要频繁更新 Embedding 和向量索引。
4. **冷启动成本高**  
    大型代码库需要先切片、向量化和建库，无法做到打开即用。
5. **检索过程不可解释**  
    Top-K 结果为什么被召回不够透明，出现错误时难以定位原因。

### 二、Claude Code 的检索三件套

#### `Glob`：查找文件

- 根据文件名模式查找，例如 `**/*.tsx`。
- 按文件修改时间倒序排列。
- 最多返回约 100 个结果，防止上下文膨胀。

#### `Grep`：搜索代码内容

- 底层使用 `ripgrep`。
- 自动遵循 `.gitignore`，避开无关目录。
- 支持正则表达式和上下文行。
- 支持三种输出粒度：
    - `content`：返回匹配内容和行号
    - `files`：只返回文件名
    - `count`：只返回匹配数量

#### `Read`：按需读取

- 默认最多读取约 2000 行。
- 支持通过 `offset` 和 `limit` 分段读取。
- 每次直接读取磁盘上的最新内容，没有索引延迟。

### 三、组合检索流程

```
Glob 找候选文件
→ Grep 定位关键词和行号
→ Read 读取相关代码
→ 根据结果继续搜索
```

它不是一次性召回全部相关内容，而是由模型根据每一步的结果动态调整下一步。

### 四、使用 Explore 子 Agent

对于需要大量搜索的开放式任务，主 Agent 会派出独立的 Explore Agent：

- 具有独立上下文。
- 主要使用只读工具。
- 可以多轮执行 `Grep`、`Glob` 和 `Read`。
- 不能修改代码或继续创建子 Agent。
- 最后只把整理后的结论返回主 Agent。

这样可以避免大量检索结果污染主 Agent 的上下文。文章给出的经验是：

- 预计少于约 3 次查询：主 Agent 直接搜索。
- 需要多轮开放式探索：交给 Explore Agent。
- 多个独立模块可以并行派出多个子 Agent。

### 五、与 RAG 的核心区别

|RAG|Claude Code 检索|
|---|---|
|预先切片和建立索引|使用时实时搜索|
|一次性召回 Top-K|多轮搜索、动态调整|
|语义相似匹配|精确字符和正则匹配|
|索引可能滞后|直接读取最新文件|
|召回过程相对黑盒|每一步都可以审查|

### 六、RAG 仍适用的场景

- 跨多个大型仓库检索
- 上千万行代码的全局搜索
- “寻找认证相关代码”这类纯语义查询
- 代码、文档和 Wiki 的混合知识库

**核心结论：Claude Code 不是认为 RAG 没用，而是在单仓库、实时变化、强调精确定位的编程场景中，选择让 LLM 使用基础工具进行多轮探索。检索工具负责提供能力，具体搜索路径由模型决定。**
