## 1. 什么是 Agent？与大模型有什么本质不同？

### 核心回答

Agent 是一个能围绕目标自主完成任务的 AI 系统。普通大模型更像“被动问答”，用户输入一次，模型输出一次；Agent 则能把复杂目标拆成多个步骤，结合工具、记忆和反馈持续推进，直到任务完成。
### 面试提醒

回答时要突出三点：**自主规划、真实行动、反馈闭环**。不要只说“Agent 会调工具”，因为“谁决定要不要调工具、什么时候调、调哪个”才是 Agent 的关键。

---

## 2. Agent 的基本架构由哪些核心组件构成？

### 核心回答

Agent 的基本架构通常由四个核心组件构成：**LLM、工具系统、记忆系统、规划模块**。LLM 负责理解任务和做决策，工具负责外部执行，记忆负责保存状态和历史经验，规划模块负责把复杂目标拆解成可执行步骤。
### 工程细节

工具定义里没有一行执行逻辑，只有「名字、描述、参数说明」
	实际开发中，工具描述其实是需要反复调优的
常见的规划和推理方式包括 CoT、ReAct、Plan-and-Execute。
	实际工程里经常混合使用，比如先用 Plan-and-Execute 做整体规划，每个子步骤内部再用 ReAct 调工具执行
### 面试提醒

不要只回答“LLM + 工具”。完整答案至少要包含 LLM、工具、记忆、规划四部分，并说明短期记忆与长期记忆的区别。

## 3. Workflow、Agent、Tools 的概念和区别

### 核心回答

Tools 是最小能力单元，只负责执行；Agent 是具备动态决策能力的系统；Workflow 是开发者预先定义好的确定性流程。三者的核心区别是：谁决定下一步做什么。
### 关键点

- Tools：封装好的函数，没有决策能力。
- Agent：由 LLM 在运行时动态决定下一步。
- Workflow：开发者提前写好控制流，**行为更可预测**。
- Workflow 的节点可以是 LLM、Tool，也可以是 Agent。
- 生产中常见的是**Agentic Workflow**：主流程用 Workflow 固定，局部节点嵌入 Agent（保留一定的灵活性）。
### 工程话题
**Agent （防止死循环）**：
- 最大循环次数
- token 预算
- 超时时间
- 停止条件
**好工具的设计原则**：
- 指责单一
- 描述精确
- 错误信息清晰（要让llm看懂）
- 参数设计简洁

## 4. Agent 设计范式与 Workflow 的区别

### 核心回答

Agent 和 Workflow 最大的区别仍然是“谁来决定下一步”。Workflow 的流程由开发者写死，确定性高、容易调试；Agent 由 LLM 动态决策，灵活但不可控。常见 Agent 设计范式包括 ReAct、Plan-and-Execute、Reflection。

### 关键点

- 纯 Agent 灵活但成本、稳定性和可观测性较差。
- 生产实践更倾向 Agentic Workflow。

### 面试提醒

可以强调一个工程原则：能用 Workflow 解决的问题，优先用 Workflow；只有节点确实需要灵活判断时，再引入 Agent。

## 5. Agent 推理模式有哪些？ReAct 是什么？怎么实现？

### 核心回答

常见推理模式包括直接回答、CoT 和 ReAct。CoT 让模型显式写出推理过程；ReAct 在 CoT 基础上加入工具行动，让模型按“思考 -> 行动 -> 观察”的循环推进任务。
### 关键点

- 直接回答：无中间推理，简单但容易跳步出错。
- CoT：显式展示推理链，提高多步推理准确率。
- ReAct：Reasoning + Acting，把推理和工具调用交织起来。
- ReAct 的循环不是模型自己自动跑，而是代码框架驱动。
- 代码负责解析模型输出、执行工具、把 Observation 写回上下文，再调用模型。
### 工程细节

ReAct 的两个实战局限（**循环漂移和错误传播**）
实际项目中两者经常混合使用（规划用大模型、执行用小模型）
### 面试提醒

最重要的是说清分工：**模型每次只输出 Thought 和 Action，外部代码负责循环、工具执行、结果回填和终止判断**。

## 6. ReAct、Plan-and-Execute、Reflection 的区别与选型

### 核心回答

ReAct 适合边想边做，灵活但长任务容易跑偏；Plan-and-Execute 适合先规划再执行，结构清晰但实现更复杂；Reflection 不是独立完整流程，而是叠加在前两者上的质量增强机制。
### 关键点

| 范式 | 核心机制 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| ReAct | 思考、行动、观察循环 | 灵活、实现简单 | 长任务易漂移，错误会传播 | 信息搜索、简单助手、开放问答 |
| Plan-and-Execute | 先规划，后执行 | 全局清晰，不易跑偏 | 初始成本更高，灵活性较弱 | 深度研究、报告生成、多工具协作 |
| Reflection | 生成、评估、改进 | 提升质量，减少错误 | 增加 token 和延迟 | 代码、报告、严谨文档等高质量场景 |
### 面试提醒

选型口诀：**简单任务用 ReAct，长流程复杂任务用 Plan-and-Execute，高质量要求再加 Reflection**

## 7. 复杂任务如何拆分？为什么要拆分？

### 核心回答

任务拆分是为了降低复杂度。LLM 一次性处理大任务容易出现**上下文过长、状态混乱、推理跳步**等问题；把任务拆成小步骤后，每一步更聚焦，也更**容易验证、重试和并行执行**。
### 关键点

- 拆分原因：降低推理难度，减少上下文压力，提高可验证性。
- **静态拆分**：开发者提前写好流程，稳定可控。
- **动态拆分**：LLM 根据目标自动规划步骤，更灵活但不稳定。
- 拆分后要分析依赖关系，能**并行的步骤并发执行**。
- **粒度要适中**，按“原子操作”划分，避免过粗或过细。
- **自适应拆分**：在执行过程中根据每一步的实际难度动态调整
	先让执行器尝试完成当前任务，如果做得好就继续往下走，不做多余的拆分；如果明显做不好，比如超过了最大步数还没完成，或者输出质量不达标，就把这个「做不好的任务」交给规划器，让规划器把它进一步拆成更小的子任务，然后对每个子任务重复同样的流程：先试，做不好就再拆。
- 拆分结果的验收标准：完备性、独立性、可验证性
### 面试提醒

完整回答要覆盖三个层次：为什么拆、怎么拆、拆完如何调度。并行执行可以显著降低端到端延迟，但前提是正确识别步骤依赖。

## 8. AI Agent 的记忆机制如何设计？

### 核心回答

Agent 需要**记忆来维持多步任务状态**，并在**跨任务场景中积累用户偏好和历史经验**。记忆可以分为感知记忆、短期记忆、长期记忆、实体记忆。
### 关键点

- 感知记忆：当前输入的原始信息，生命周期最短。
- 短期记忆：context window 内的对话历史和任务状态。
- 长期记忆：存储在外部数据库中，可跨任务复用。
	**长期记忆还可以细分**
    - **情节记忆**：具体发生过的任务经历。
    - **语义记忆**：从多次经历中总结出的通用知识。
    - **程序记忆**：可复用的操作流程或 SOP。
- 实体记忆：从对话中抽取出的结构化事实，如用户偏好、项目属性。
### 工程细节

1. **设计记忆模块的三个核心问题**
    - **存什么**：只存下次任务会用到的信息，比如**用户偏好、关键结论、外部知识**；不要把闲聊、原始日志、中间推理全存进去。
    - **怎么存**：非结构化文本适合向量数据库，结构化偏好适合关系数据库或 KV 存储，主流做法是混合存储。
    - **什么时候取**：任务开始前**主动检索**用户背景和偏好；任务执行中如果需要特定知识，再**按需检索**。
2. **知识图谱的作用**  
    向量数据库适合语义相似检索，但不擅长处理实体关系。  
    知识图谱可以用“**实体 -> 关系 -> 实体**”的形式保存信息，支持多跳推理，适合处理用户、公司、项目、角色之间的关系。
3. **记忆整合**  
    长期记忆用久了会变碎、重复、过期甚至冲突，所以要定期做：
    - 去重
    - 冲突消解（时间戳）
    - 抽象提炼  
        比如把多次具体失败经历总结成一条通用经验。
### 面试提醒

可以用“读 -> 用 -> 写”描述记忆闭环：任务开始前检索相关记忆，执行中注入上下文使用，任务结束后沉淀有价值的新信息。

## 9. 长短期记忆系统怎么做？记忆怎么存、粒度是多少、怎么用？

### 核心回答

**短期记忆通常就是上下文窗口里的对话历史和中间状态，任务结束后清理；长期记忆通常通过 Embedding + 向量数据库实现，用语义检索召回相关信息，再注入 prompt。**
### 关键点

- 短期记忆：当前任务工作台，存最近对话、工具结果、中间状态。
- 长期记忆：跨任务知识库，用向量数据库或关系数据库保存。
- **语义内容适合向量检索，结构化偏好适合关系型存储。
- 存储粒度建议是“一次完整交互”或“一个独立知识点”。
- 太细会碎片化，太粗会影响召回精度。
### 工程细节
1. **结构化工作记忆**  （短期中用）
    普通短期记忆只是不断追加消息，容易变乱。  
    更好的方式是把工作区结构化，比如分成：
    - 当前任务目标
    - 已确认结论
    - 待验证假设
    - 工具结果
    - 当前进度
2. **记忆衰减**  （长期中用）
    长期记忆不是永久可信的。旧记忆可能过时，比如用户半年前说学 Go，现在一直在写 Python。  
    所以可以给**记忆加新鲜度权重**，或者定期清理、合并、标记失效。

## 10. 什么是 Multi-Agent？

### 核心回答

Multi-Agent 是多个 Agent 协作完成任务的系统。每个 Agent 可以承担不同角色，如搜索、写作、编码、评审、调度等。它解决的是**单 Agent 在上下文容量、专业分工和并行执行上的限制**。
### 关键点

- 单 Agent 受 context window 限制，复杂任务信息容易撑爆上下文。
- 单 Agent 做所有事情容易变成“泛才”，专业度不足。
- 多 Agent 可以让每个 Agent 拥有更干净、更聚焦的上下文。
- 多个 Worker 可以并行执行子任务，提高效率。
- Multi-Agent 更适合长流程、复杂、可拆分任务。
### 面试提醒

回答时不要只说“多个 Agent 效率更高”，要说出技术驱动因素：上下文限制、专业分工、并行执行。

---

## 11. Single-Agent 和 Multi-Agent 的设计方案

### 核心回答

Single-Agent 适合流程清晰、复杂度适中的任务，实现简单、维护成本低；Multi-Agent 适合需要**专业分工、子任务并行、上下文容易超限**的复杂任务。Multi-Agent 架构常见中心化 Orchestrator 模式和去中心化 Peer-to-Peer 模式。
### 关键点

- Single-Agent：简单、可控、调试成本低。
- Multi-Agent：适合专业角色拆分和并行执行。
- Orchestrator：一个主 Agent 负责任务拆分、调度和汇总。
- Peer-to-Peer：Agent 之间直接通信，灵活但难控制。
- 工程生产里更常用 Orchestrator，因为可观测、可追踪、好排查。
### 面试提醒

不要简单说“复杂任务用 Multi-Agent”。更准确的标准是：是否会撑爆上下文、是否需要明显专业分工、是否存在可并行子任务。

## 12. Agent 记忆压缩有哪些方法？

### 核心回答

记忆压缩常见方法包括**摘要压缩、滑动窗口、重要性过滤、结构化抽取**。它们解决的是上下文过长、信息噪音大、记忆载体不够高效的问题。
### 关键点

- **摘要压缩**：把长对话压成短摘要。
	层级摘要：
		分层处理：最近 10 轮保持原文，10 到 50 轮的历史压缩成一份「中期摘要」，50 轮之前的历史进一步压缩成更精炼的「长期摘要」。
		好处：Agent 既能精确回忆近期细节，也能粗略回忆远期要点，比一刀切的摘要颗粒度更合理。
- **滑动窗口**：只保留最近 N 轮上下文。
- **重要性过滤**：给信息打分，只保留高价值内容。
- **结构化抽取**：把关键信息转成结构化字段保存。
- 常见组合：滑动窗口丢弃旧内容前，先做摘要保留关键信息。
### 工程

选方案的时候，可以按这个思路来判断：对话不长、业务简单的场景，滑动窗口就足够了，实现成本最低；对话会很长但不想硬截断的场景，摘要加滑动窗口的组合是最稳健的工程选择；如果业务里有明确定义的「关键信息」（用户偏好、确认事项、状态字段），结构化抽取的信息密度最高，效果也最好；高频调用、长 prompt、成本敏感的系统，Prompt Caching 的收益非常可观，值得优先考虑。
### 面试提醒

Prompt Caching 不是记忆压缩。它是计算层优化，用来减少重复上下文的计算成本；记忆压缩是信息层优化，用来决定哪些内容该保留和如何保留。

## 13. 为什么有时候选择手写 Agent，而不是直接用成熟框架？

### 核心回答

成熟框架适合 POC 和快速验证，但在生产环境中可能带来**抽象层过多、调试困难、版本升级破坏、性能开销和业务定制不灵活**等问题。手写 Agent 的核心价值是**可控、可观测、可优化**。
### 关键点

- 框架优点：启动快、封装好、适合原型验证。
- 框架痛点：抽象层复杂，出问题难定位。
- 版本升级可能引入 breaking change，影响稳定性。
- 通用框架可能不贴合业务流程，定制成本高。
- 务实策略：核心逻辑手写，边缘工具能力复用框架。

[AgentScope 2.0](../04-References-%E9%A1%B9%E7%9B%AE%E5%8F%82%E8%80%83/AgentScope.md) 是这一取舍的具体案例：它能复用 ReAct、事件流、权限、Workspace 和服务化骨架，但项目仍要承担框架版本、状态迁移和业务定制成本。
### 面试提醒

不要一味否定框架。更成熟的回答是：POC 用框架提速，生产核心链路倾向手写，周边能力适当借用框架。

## 14. 如何赋予 LLM 规划能力？

### 核心回答

给 LLM 增强规划能力，常见方法包括 CoT、ToT 和 GoT。CoT 让模型线性展开推理步骤；ToT 让模型探索多条推理路径并选择更优路径；GoT 使用图结构组织推理节点，可以复用和合并中间结论。
### 关键点

- **CoT：成本最低，通过 prompt 让模型显式推理。缺点：没有任何纠偏机制**
	- 第一种叫 Zero-shot CoT，就是直接在 prompt 末尾加「让我们一步步思考」，LLM 自己展开推理，不需要额外例子；
	- 第二种叫 Few-shot CoT，给几个带有完整推理过程的例子，让 LLM 模仿这种推理格式来回答新问题，效果通常更稳定。
- ToT：多路径搜索，能纠偏，但调用成本更高。（**生成-评估-剪枝**）
- GoT：图结构推理，可**复用中间结论**，适合复杂问题。
- CoT 是规划能力的一种基础实现，不等于规划能力本身。
- **工程中 CoT 最常用，ToT 要考虑成本，GoT 更偏研究阶段。**
### 工程细节

工程上一般用：Plan-and-Execute 的核心价值就是：先用一次 LLM 调用建立全局视角，再用后续调用逐步落地，把「规划」和「执行」分成两个阶段来做。
每执行完一步，会有一个 **Re-planner（重新规划器**回顾当前进展，判断原来的计划还适不适用，如果中间发现了新的信息或者某步执行结果不符合预期，就动态调整后续步骤

## 15. Agent 的反思机制是什么？为什么要用？怎么实现？

### 核心回答

反思机制是让 Agent 在完成一个步骤或任务后，对结果进行自我评估，如果发现问题，就根据评估意见重新生成或修正。它的本质是“**生成 -> 评估 -> 改进”的闭环**。
### 关键点

- 反思不是简单重试，而是有**评估标准的定向改进。
- 通常会设计两个 prompt：**评估 prompt 和改进 prompt**。
- 评估 prompt 要包含具体检查维度，比如**事实、逻辑、完整性、表达**。并设置 **PASS 出口**。
- 反思可分为**步骤级反思和任务级反思**。
- **必须设置最大轮次**，常见是 2-3 轮，防止死循环。
### 工程细节

**为什么要用反思**  
   LLM 第一次输出往往不是最优，可能存在：
   - 逻辑跳跃
   - 细节遗漏
   - 事实错误
   - 表达含糊

 **多 Agent 互评**
   除了自我反思，还可以设置独立的 `Critic Agent` 审查输出。  
   这种方式通常比自我检查更客观，因为同一个模型容易对自己的输出产生“自洽偏见”。

**进阶机制**
   - **Reflexion**：不只改当前输出，还会把失败经验存入记忆，下次遇到类似任务时参考。
   - **LATS**：把反思和树搜索结合，多路径探索并从失败路径中学习，成本更高，偏研究场景。

 **工程取舍**
   反思能提升质量，但代价是更多 LLM 调用、更高 token 成本和更长延迟。  
   所以工程上通常只在关键节点使用，比如最终报告、代码生成、重要决策分析。简单问答、格式转换、实时性要求高的场景不适合频繁反思。

**面试重点：**  
回答时要强调：反思机制的本质是 **生成 -> 评估 -> 改进**，不是“不满意就重试”。还要说出评估 prompt 的检查维度、`PASS` 出口、最大轮次限制，以及步骤级/任务级反思的取舍

## 16. 如何设计多 Agent 的协作与动态切换机制？

### 核心回答

协作靠两件事：**消息传递和共享状态**。消息传递是 Agent 完成自己的工作后把结果发出去，下一个 Agent 取用；共享状态是所有 Agent 共同读写一个状态对象，记录任务进展和中间结果。

**动态切换靠 Orchestrator**来做，有两种方式：一种是静态路由，提前写好规则「任务类型 A 就找 Agent X」；另一种是让 LLM 动态决策，根据当前情况实时判断该把任务交给谁。

我的实践是两种混用，**主流程用静态路由保证稳定，边缘情况才交给 LLM 动态判断**。
### 关键点

- **消息传递**：Agent 完成任务后发出结果，下游 Agent 取，需要**消息中间件来维护**，优点是解耦，发送方不用知道接收方是谁。
- **共享状态**：所有 Agent 共同读写同一个 State，前一个 Agent 写入结果，后一个 Agent 直接读取
- 静态路由：规则固定、稳定可预测。

- 动态路由：LLM 根据上下文判断，灵活但不可控且成本更高
	核心就是让 LLM 做一次分类决策，把可用的 Agent 列表和当前上下文传给它
	实际项目里通常还会加一些保护措施，比如校验返回的 Agent 名称是否在可用列表中、设置默认的 fallback Agent、记录路由决策的日志以便后续分析等

### 工程细节

**共享状态的设计要点**  
    多 Agent 共用状态时很容易出 bug，为了**避免结果互相覆盖、读取到脏数据、状态混乱**：
    
    - 状态要分层：全局状态放公共信息，局部状态放各 Agent 自己的中间结果。
    - 写入规则要明确，最好“只追加不覆盖”，做增量更新，避免互相覆盖。
    - 错误状态也要写入 State，方便后续 Agent 或 Orchestrator 判断是重试、跳过还是终止。
### 面试提醒

多 Agent 协作要设计通信方式、共享状态、路由机制和异常处理。消息传递强调**解耦**，共享状态强调直接；静态路由稳定，动态路由灵活，生产中通常用“静态路由保底 + 动态路由兜底”的混合策略。
